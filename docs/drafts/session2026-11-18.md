## Session 2

**Topic:** Design document review and completion — sections 5, 7, 8, and 9.

### Section 5 — Workflows

Section 5 was originally limited to the maintenance ticket workflow only. It was expanded to cover all major workflows in the system:

- **5.1 Maintenance ticket** — existing content reorganised under the new section structure.
- **5.2 Lease lifecycle** — state diagram and rules. Initially included a Scheduled state for future-dated leases, then simplified to a single Active state after deciding the manager just sets the start date regardless of whether it is today or a future date.
- **5.3 Move-out request** — state diagram covering Pending, Approved, Rejected, and Cancelled. Includes the `can_request_move_out` flag on the Lease entity, pre-conditions for finalising a move-out, and the rule that open tickets must have `created_by` reassigned to the manager before finalising.
- **5.4 Payment and charge** — state diagram with derived states (Unpaid, Partially Paid, Paid, Voided). Manager-only voiding with required reason.
- **5.5 Account lifecycle** — deactivation, reactivation rules per role, and the rehire-as-new-account decision.
- **5.6 Employee onboarding and termination** — onboarding steps, termination state diagram with a PendingTermination blocker state when open tickets exist.

### Section 7 — Business rules

Two rules were added:
- A tenant can have at most one active lease at a time, enforced by a partial unique index on `lease(tenant_id) WHERE status = 'Active'` and a domain pre-check.
- The `can_request_move_out` flag on Lease controls whether a tenant can submit a move-out request.

### Section 8 — Decision log

All open items from section 9 were resolved and recorded here. New subsections added:

- **Architecture** — Clean Architecture, four layers (Domain, Application, Infrastructure, API), one test project per layer, PostgreSQL via EF Core, Blazor WebAssembly frontend.
- **Technical conventions:**
  - Authentication: JWT, HttpOnly cookies, 30-minute access token, 7-day refresh token rotated on use.
  - Error format: Problem Details (RFC 7807).
  - API versioning: skipped, noted as a future improvement.
  - Logging: Serilog from the start, console sink for local development.
  - Local startup: Docker Compose for PostgreSQL only, `dotnet run`/`dotnet watch` for API and frontend.
- **Bootstrapping** — EF Core data seeder on startup, credentials from environment variables, one admin account seeded, `.env.example` file to be created alongside the seeder.
- **Dismissing a category review request** — a manager can dismiss with a required comment, recorded as a `CategoryReviewDismissed` event. Ticket stays Open, category and assignment unchanged.
- **Technician unavailable after work has started** — cancel the ticket with a comment and open a new one.
- **Editing other users' profile data** — managers can edit any user's name, phone, and date of birth. Admins can edit the same fields for manager accounts only. Auditing is a future improvement.
- **Financial milestone** — time entries, charges, payments, and financial reports ship together after the core system is complete.
- **Move-out re-submission after rejection** — tenant cannot resubmit until a manager explicitly re-enables it via a dedicated action. Automatic re-enabling rules are a future improvement.
- **Employee lifecycle decisions:**
  - Rehire creates a new account.
  - Terminated employee history remains visible to managers.
  - A technician with open assigned tickets cannot be terminated until all tickets are reassigned to the manager handling the termination.
  - Tenant reactivation requires a new active lease. Employee reactivation follows the onboarding workflow.
- **Lease lifecycle decisions:**
  - No overlapping leases — current lease must end before a new one is created.
  - Unpaid charges survive lease end.
  - Renewal means extending the end date, not closing and reopening.
- **Move-out decisions:**
  - `can_request_move_out` flag lives on Lease, not Tenant.
  - Rejection sets the flag to false. Re-enabling is a deliberate manager action.
  - Before finalising, all open tickets must be resolved/closed and all charges settled or voided.
- **Ticket priority** — handled outside the system for now (older = higher priority). Implementation deferred to future improvements.
